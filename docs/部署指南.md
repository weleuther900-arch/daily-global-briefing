# 部署指南

推荐使用 GitHub Actions 部署：无需购买服务器、无需保持电脑开机，工作流会在 GitHub 托管运行器上完成采集、生成、审校和可选邮件投递。它适合“每天自动运行”，但 GitHub 的 `schedule` 事件不承诺精确开始时间；如果你必须在某个具体时刻前收到邮件，请使用下方的“准点投递”方案。

## 先选择部署仓库

本项目的公开仓库用于分发代码、文档和样例，不应成为个人晨报内容的长期存储位置。工作流不会上传晨报 Artifact，也不会把抓取缓存和运行状态写入 GitHub Actions Cache；任务结束后运行器上的临时文件会被销毁。不过，公开仓库的 Actions 日志仍可能显示运行时间、成功状态和事件数量等最小元数据。

如果每日内容、来源轨迹或运行元数据需要私有，推荐创建一个**私有部署仓库**：

1. 在 GitHub 新建空白仓库，选择 `Private`，不要初始化 README 或 `.gitignore`。
2. 将本公开仓库克隆到本机，移除原远端后推送到私有仓库：

```powershell
git clone https://github.com/weleuther900-arch/daily-global-briefing.git
cd daily-global-briefing
git remote rename origin upstream
git remote add origin https://github.com/YOUR_ACCOUNT/YOUR_PRIVATE_REPOSITORY.git
git push -u origin main
```

3. 在私有部署仓库中继续下面的 Secrets 和 Actions 设置；公开仓库可保留为 `upstream`，用于按需同步代码更新。

直接 Fork 适合想公开自己的配置或仅试用项目的使用者，但不建议用公开 Fork 承载私人晨报。

## 部署前准备

你需要：

1. 一个 GitHub 账号；
2. 一个 DeepSeek API 密钥；
3. 一个可用于 SMTP 投递的 Gmail 账号与应用密码；
4. 发件地址和收件地址。

项目默认使用 DeepSeek V4 Flash 成稿、DeepSeek V4 Pro 复核。若不需要官方 X 帐号动态，可不配置 X API 凭据。

## 最短部署路径

### 1. Fork 仓库

在仓库页面点击 **Fork**，创建自己的副本；或者按上一节创建私有部署仓库。所有后续 Secrets 和工作流运行都位于你的部署仓库中。

### 2. 启用工作流

进入你的仓库的 `Actions` 页面，选择 **Daily Global Briefing**，点击 **Enable workflow**。

公开仓库 Fork 的定时工作流默认被禁用；GitHub 也可能在公开仓库 60 天没有活动后自动禁用定时工作流。工作流必须保留在默认分支上，重新启用后会继续按计划运行。[GitHub 官方说明](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows) 和 [定时事件说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)。

### 3. 添加 GitHub Secrets

进入 `Settings → Secrets and variables → Actions → New repository secret`，逐项添加：

| 名称 | 值 | 说明 |
| --- | --- | --- |
| `DEEPSEEK_API_KEY` | 你的 DeepSeek API 密钥 | 必需，用于成稿与复核 |
| `GMAIL_APP_PASSWORD` | Gmail 应用密码 | 必需，只用于 SMTP 验证 |
| `BRIEFING_SENDER_ADDRESS` | 发件邮箱 | 必需 |
| `BRIEFING_RECIPIENT_ADDRESS` | 收件邮箱 | 必需；可与发件邮箱相同 |
| `ENABLE_EMAIL_SEND` | `false` | 必需；首次测试期间保持关闭 |
| `X_BEARER_TOKEN` | X API Bearer Token | 可选；不填即跳过 X 来源 |

Secrets 需要在工作流中显式映射为环境变量才可被读取；本项目已在工作流中完成映射。[GitHub Secrets 官方说明](https://docs.github.com/en/actions/concepts/security/secrets)。不要将这些值写入 YAML、`.env.example`、Issue 或提交记录。

### 4. 先运行安全检查

进入 `Actions → Daily Global Briefing → Run workflow`，选择：

- `mode`：`scan`
- `allow_send`：保持 `false`

该模式只检查来源与覆盖，不调用模型、不发送邮件。来源健康状态和覆盖组结果会显示在工作流日志中；工作流不上传晨报、审计文件、抓取缓存或状态文件。

### 5. 发送一次版式测试

确认扫描正常后，将 `ENABLE_EMAIL_SEND` 改为 `true`，再手动运行工作流：

- `mode`：`layout-test`
- `allow_send`：`true`

确认收到的测试邮件在常用客户端中显示正常。随后保留 `ENABLE_EMAIL_SEND=true`，定时任务会按默认时间表运行。

## 默认时间表

| 北京时间 | 模式 | 用途 |
| --- | --- | --- |
| 07:05 | `final`（Cloudflare） | 外部 UTC Cron 准点派发正式晨报 |
| 07:35 | `final`（Cloudflare 兜底） | 首次未投递时再次派发；运行锁和发送状态防止重复模型调用与邮件 |
| 07:50 | `final`（GitHub schedule） | 仅当 Cloudflare 两次派发均失败时的最后云端兜底；已投递则从私有状态幂等退出 |
| 15:23 | `scan` | 日内来源巡检 |
| 每周日 23:10 | `case` | 商业案例生成与可选投递 |

GitHub Actions 的 `schedule` 使用 UTC，且高负载时可能延迟或丢弃排队任务，因此 Cloudflare Workers Cron 仍是主触发器：它在 23:05 和 23:35 调用 GitHub `workflow_dispatch`，即北京时间 07:05 和 07:35。GitHub 另在 UTC 23:50（北京时间 07:50）保留一次正式晨报兜底：仅当两次外部派发失败时才会继续执行；首次成功投递后，兜底任务会从私有运行状态幂等退出，不调用模型也不重复发信。所有模型请求仍有运行时硬门禁：只允许在北京时间 23:00 至 08:30 发起；晚于 08:30 的任务会记为 `model-window-stopped`，不会连接模型服务商或发送邮件。

外部 Cron 能移除 GitHub `schedule` 的不确定性，但 GitHub 执行器本身仍可能排队，所以它是显著降低失败概率而非对收件时间的数学保证。07:35 的兜底点留出了到 08:30 的缓冲；如果两次派发都未形成 SMTP 250，必须从 Cloudflare 和 GitHub 日志排障，不能把“已派发”称为“已投递”。

若晨报已经生成但因邮件服务故障未投递，可在私有部署仓库手动选择 `resend`，填写原始 Actions 运行编号和 `allow_send=true`。该模式仅下载私有归档中的已选事件并重建邮件，**不调用模型**；归档默认保留 14 天。

## 准点投递：Cloudflare Workers Cron（推荐）

仓库中的 [`cloudflare-scheduler`](../cloudflare-scheduler) 是一个没有公网业务接口的最小 Worker：它只能在两个 Cron 时刻向指定私有仓库派发 `daily-briefing.yml` 的 `mode=final`、`allow_send=true` 和 `trigger_source=cloudflare-cron`。它不保存晨报正文、来源、邮箱地址、模型密钥或 SMTP 凭据；这些仍只留在私有 GitHub Actions 配置中。

```text
Cloudflare UTC Cron (23:05 / 23:35)
  → GitHub workflow_dispatch (private main)
  → 来源、时间、预算、结构与独立证据门禁
  → SMTP 250 才算实际投递
```

首次部署在私有部署仓库中完成：

1. 为保证 Wrangler 配置、登录状态和 npm 缓存均留在项目目录，在 PowerShell 中先设置一次当前会话环境，再进入 `cloudflare-scheduler` 运行安装与登录：

   ```powershell
   $briefingRoot = 'E:\AI\daily-global-briefing'
   $env:XDG_CONFIG_HOME = Join-Path $briefingRoot '.tools\xdg-config'
   $env:npm_config_cache = Join-Path $briefingRoot '.cache\npm'
   npm install
   npx wrangler login
   ```

   这不会把令牌写入仓库；`.tools`、`.cache` 与 `node_modules` 均被 Git 忽略。
2. 在 GitHub 创建一个仅限 `weleuther900-arch/daily-global-briefing-private` 的细粒度个人访问令牌，只授予 **Actions: Read and write**。不要使用宽泛的 classic `repo` 令牌。
3. 运行 `npx wrangler secret put GITHUB_DISPATCH_TOKEN`，在交互提示中粘贴该令牌。不要将令牌写进 `wrangler.jsonc`、`.dev.vars`、项目日志或 Git。
4. 运行 `npm test` 和 `npx wrangler deploy`。`wrangler.jsonc` 是 Cron 的唯一配置源；不要再在 Cloudflare Dashboard 手工新增同名 Cron。
5. 部署后在 Cloudflare Workers 日志确认两个 UTC Cron 已存在，并在下一次触发后确认日志有 `github-workflow-dispatch-accepted`。然后到 GitHub Actions 核对 `TRIGGER_SOURCE=cloudflare-cron`、运行状态和最终 `sent=true`/SMTP `250`。

Cloudflare 的 Cron 配置变更可能需要最多约 15 分钟传播，因此应在下一次晨报前至少 15 分钟完成部署。若你的私有仓库或默认分支不同，先修改 `wrangler.jsonc` 中的 `GITHUB_REPOSITORY` 与 `src/index.js` 中的 `BRANCH`，再部署；不要通过环境变量或日志输出令牌。

## 本机触发（仅作备份）

如果 Cloudflare 不可用且你愿意保持一台电脑开机，可用 Windows“任务计划程序”调用 `workflow_dispatch` 作为备份。不要删除当前的 `schedule` 块：它仍负责 15:23 巡检与周度案例；本机任务只派发 `final`。

仓库提供了不含任何个人信息的触发脚本：[dispatch-workflow.ps1](../scripts/dispatch-workflow.ps1)。需要本机已经安装并登录 GitHub CLI（`gh auth login`）。下面的示例建立 07:05 的正式触发和 07:40 的兜底触发；工作流按当天运行状态幂等处理，第一次已成功投递时，第二次不会重复调用模型或重复发信。

```powershell
$root = 'C:\path\to\daily-global-briefing'
$repo = 'YOUR_ACCOUNT/YOUR_PRIVATE_REPOSITORY'
$settings = New-ScheduledTaskSettingsSet -StartWhenAvailable -WakeToRun

foreach ($time in @('07:05', '07:40')) {
  $taskName = "DailyGlobalBriefing-Final-$($time.Replace(':', ''))"
  $arguments = "-NoProfile -ExecutionPolicy Bypass -File `"$root\scripts\dispatch-workflow.ps1`" -Repository `"$repo`" -Mode final"
  $action = New-ScheduledTaskAction -Execute 'powershell.exe' -Argument $arguments
  $trigger = New-ScheduledTaskTrigger -Daily -At $time
  Register-ScheduledTask -TaskName $taskName -Action $action -Trigger $trigger -Settings $settings -Description 'Dispatches the private Daily Global Briefing workflow.' -Force
}
```

启用 `WakeToRun` 后，支持唤醒的电脑会在任务时刻尝试唤醒；电脑仍需有电、网络和有效的 GitHub CLI 登录。可以先用 `-Mode scan` 手动运行脚本验证触发链路；该模式不会调用模型或发送邮件。

## 常见问题

### 工作流没有按时运行

确认工作流位于默认分支、已经启用，并检查是否因长期无活动而被 GitHub 暂停。可手动运行一次 `scan` 重新验证。

### 工作流没有发送邮件

检查 `ENABLE_EMAIL_SEND` 是否为严格的 `true`，并确认四个必需 Secrets 均已配置。缺少地址、应用密码或发送开关时，系统会在建立 SMTP 连接前停止。

如果日志显示 `534 5.7.9 Application-specific password required`，请不要填 Gmail 登录密码。用发件 Gmail 账号完成以下操作：

1. 在 Google 账号中开启两步验证；
2. 打开[Google 的“应用专用密码”页面](https://myaccount.google.com/apppasswords)，新建一个名称如 `Daily Global Briefing` 的密码；
3. 将显示的 16 位密码填入私有仓库 `Settings → Secrets and variables → Actions → GMAIL_APP_PASSWORD`，覆盖旧值；
4. 重新手动运行 `layout-test`，并把 `allow_send` 设为 `true`。

修改 Google 账号登录密码会使已有应用专用密码失效，届时按上述步骤新建并替换即可。

### 来源覆盖不足

先运行 `scan`，查看日志与审计产物中失败的覆盖组。单一来源暂时不可用不一定会阻断运行；只有覆盖组低于最低可用入口数时才会停止正式任务。你可以在 [`config/sources.v1.json`](../config/sources.v1.json) 增加符合来源规则的备用入口。

### 成本超过预期

默认只启用 10 元人民币的月度预算门槛；每日 Token 上限默认关闭。月度门禁以当前官方常规价格的两倍预留，覆盖已公布的峰时加价风险；如未来需要额外限制单日消耗，可在工作流中显式设置正数 `DAILY_AI_TOKEN_BUDGET`。私有部署会把每次运行的实际 Token 与成本汇总保留在审计产物中。模型平台如临时调整价格，仍应以其余额或平台配额作为最终外部上限。

## 升级与自定义

定期从上游同步代码，并在更新来源注册表、工作流或模型配置后先运行 `npm test`。你的 Secrets 不会随 Git 同步；无论 Fork 还是私有部署仓库，都需要独立维护它们。
