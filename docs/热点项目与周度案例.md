# 热点项目与周度案例

## GitHub：发现近期关注度上升

`github-rising` 替代直接抄录榜单的入口。搜索近期新建和近期活跃仓库，结合 GitHub Trending 线索，并查询 GitHub 官方 Star 历史汇总。日榜和周榜是内部发现渠道，不是固定栏目，也不是自动入选凭据。

判断依赖近期新增或净增，而非累计 Star 排名。小项目同时满足新增数量和增长比例才进入候选，避免极小基数造成夸张百分比。默认工程阈值在来源配置中可调整：一天新增/折算日均净增至少100；或净增至少30且增长10%；一周新增/折算净增至少500；或净增至少100且增长25%。官方当前周中某个自然日新增达到100也可作为近期关注信号。阈值只筛候选，主题、用途、证据和成稿仍要经过审校。

三种口径必须分开：

- 官方历史接口：按平台自然周与自然日统计新增；最新一周可能尚未结束，未来日零值不能解释为降温。其日界线不保证与 UTC 一致，不称精确滚动24小时或7天。
- Trending：保留平台的 `today` / `this week` 新增及出处，不擅自换算周期。
- 连续快照：约一天和一周的净变化，记录实际起止时间与小时数；净增包含取消 Star 的影响。有相邻可比区间才计算加速比。

没有历史证据时只记录观察对象，不用累计量推算增长。已离开榜单的对象继续轮换观测。当前每轮两次搜索各最多30个结果、最多24个已观察项目补查、最多24个项目核验官方历史、最多8个热门项目补取README，不宣称覆盖全站。查询失败单独记录，不能写成零增长；原始快照保存于 `.cache/discovery/github-star-history.json`，保留35天、最多500个仓库，不提交源码仓库。

输出应讲清项目用途、关注度证据、可能的商业影响以及判断边界。仓库介绍是作者声明，Star不是用户数、实际采用率或成功证明；公开仓库不自动等于已核实可商用许可。观察时间明确区别于项目发布日期。

依据：[GitHub搜索接口](https://docs.github.com/en/rest/search/search#search-repositories)、[GitHub Star历史汇总](https://docs.github.com/en/rest/activity/starring#get-repository-star-history)。

## 周度案例：选题、审校和恢复

从独立来源池搜集素材，按同一主体组织至少3份、最多5份可核实材料。目标是解释一个有事实支撑的经营问题，覆盖背景、选择与约束、商业模式、竞争及结果；缺少经营数据就明确缺失，不凭产品公告编造单位经济或现金流。末尾练习题仍沿用原有不附标准答案要求，讲解与练习的最终比例另行确认。

独立审校拒绝后，最多修复一次并重新审校；仍失败可尝试第二个独立选题。调用继续受预算与时间门禁约束，不为按时发送放行未通过审校的内容。

已通过审校的稿件先保存，再尝试投递。SMTP失败后的备用运行复用已审稿件；同一周跨日补跑仍使用周日日期。SMTP接受回执写入发送记录后，后续补跑按周去重。这降低重复投递概率，但SMTP接受与本地记录之间的进程中断仍无法保证严格“恰好一次”。

私人部署以北京时间周日20:00为主触发，GitHub备用触发为周日20:30、22:30和周一05:30。允许周度案例任务执行到周一08:30，容纳定时任务排队延迟。公开示例部署的具体调度和缓存策略以其工作流为准。

`--mode case --validate-only` 只检查真实素材，不调用模型、不发送邮件；可以在工作日验证。测试使用模拟模型和SMTP验证修复、换题、防重及投递恢复，不能把这些结果称作真实周报已发送。未来投递仍需以运行记录中的SMTP回执验收。
